Product Story

产品故事：为什么做「搭子成行」

一切从一个真实的校园观察开始。

📍

问题发现

在校园生活中，我注意到一个普遍现象：很多同学想出去玩、想拼餐、想运动，但找不到同行的人。不是没有社交意愿，而是缺少一个低门槛、有信任感的匹配工具。现有的解决方案——微信群喊人（效率低、无信任）、社交App（目的不纯、压力大）、旅行社跟团（自由度低）——都无法满足这个需求。

📋

需求验证（拒绝自嗨）

设计调研问卷，通过校园群、朋友圈发放，回收 52 份有效问卷。同时招募 10 位同学进行 20-30 分钟的半结构化访谈。用 KANO 模型对需求进行分类，结论是：「安全信任」是基本型需求（没它不行），「兴趣匹配」是期望型需求（越好越满意），「社交游戏化」是兴奋型需求（超出预期）。

🎨

产品设计

基于调研结论，确定产品定位：面向 18-28 岁独居/在校青年的轻社交搭子匹配平台。规划四大核心模块（发布行程 → 智能匹配 → 即时沟通 → 履约评价），覆盖拼餐、运动、学习、探店、观影、游戏 6 大场景。使用 Figma 输出 18 个页面的高保真可交互原型。

🤖

AI 辅助开发

借助 Cursor（AI 编程工具）完成前端页面与后端逻辑的实现。这个过程中最大的收获不是代码本身，而是深刻理解了「需求描述的精确度如何影响开发产出」——这本质上是产品经理与工程师沟通的微缩版训练。输出完整 PRD（含功能详述、交互规则、数据埋点方案、验收标准）。

🚀

冷启动 + 数据迭代

在校园内通过朋友圈、班级群、社团群推广，2 周获得 80+ 注册用户，完成 20+ 次成功匹配。通过数据分析发现初版匹配算法的兴趣维度权重过低，调整后匹配成功率从 40% 提升至 65%。完成了「发现问题 → 提出假设 → 上线验证 → 数据复盘」的完整闭环。

User Research

用户研究：用数据说话，不是用感觉

📊

问卷调研（n=52）

曾因找不到人而放弃出行78%

🎙️

深度访谈（n=10）核心发现

  • 安全是第一门槛：8/10 受访者提到「希望看到对方的基本信息和历史评价」，信任机制比匹配算法更重要
  • 「轻社交」定位最受欢迎：用户想要的是「一起做件事」，而不是「交个朋友」——降低了心理门槛
  • 时间窗口很窄：大多数用户的决策窗口在出行前 1-3 天，产品需支持快速匹配
  • 学生身份是信任加速器：同校/同城学生之间的信任度显著高于陌生人
👩

典型用户 A：独居实习生

22 岁，刚到陌生城市实习，没有社交圈。需求：下班后找附近的人一起吃饭、运动。痛点：社交App压力大，微信群效率低。核心诉求：低门槛、就近、安全。

👨

典型用户 B：大二学生

20 岁，喜欢探店但室友爱好不同。需求：找到兴趣相投的人一起打卡。痛点：一个人去尴尬，在群里喊没人应。核心诉求：兴趣匹配、活动导向。

Feature Highlights

功能亮点与产品设计思考

🧭

6 大场景全覆盖

基于用户调研数据，覆盖拼餐、运动、学习、探店、观影、游戏 6 个最高频场景。每个场景有独立的列表页、发布页和详情模板——同一套架构支撑多场景扩展，体现了产品架构的可复用性设计。

🔐

信任与安全闭环

支持手机号验证码登录 + 微信快捷登录，补齐身份证绑定与手机号验证。信任机制是搭子类产品的第一道门槛——84% 的受访者将此列为最关心的问题，因此在产品设计中优先于匹配算法。

🧠

智能匹配算法

匹配权重设计：目的地（30%）+ 时间窗口（30%）+ 兴趣标签（25%）+ 距离/性别等其他因素（15%）。经过一轮迭代后兴趣权重从 10% 提升至 25%，匹配成功率从 40% 跃升至 65%。

💬

沟通与履约闭环

内置即时通讯降低沟通摩擦，配合评价体系构建双向反馈。完成履约后可互相评价，评价数据反哺匹配算法——好人匹配好人，形成正向循环。

📱

完整的用户路径设计

「欢迎页 → 注册登录 → 身份绑定 → 浏览匹配 → 发布邀约 → 聊天沟通 → 履约评价」7 步闭环，每一步都有明确的前置条件和后置状态，确保用户不会迷失在流程中。

🤖

AI 协同开发实践

全程使用 Cursor（AI 编程工具）完成代码实现。在这个过程中积累了 Prompt Engineering 的实战经验——需求描述越精确、上下文越完整，AI 生成的代码质量越高。这一发现直接印证了 PRD 质量对开发效率的杠杆效应。

Iteration Journey

迭代历程：从 40% 到 65% 的增长故事

产品发布只是起点，数据驱动的迭代才是产品经理的核心能力。

V1.0 · 上线首版
40%
匹配成功率
  • 匹配维度：仅目的地 + 时间
  • 兴趣标签：有收集但未参与匹配
  • 用户反馈：「推给我的人不太对」
  • 距离权重过高，忽略了偏好
数据分析 → 假设 → 验证
V1.1 · 兴趣权重迭代
65%
匹配成功率 +62.5%
  • 匹配维度：目的地(30%) + 时间(30%) + 兴趣(25%) + 其他(15%)
  • 新增「最近使用」「常用分类」快捷入口
  • 用户反馈：「这次推的人好多了」
  • 好评率从 72% 提升至 85%

💡 这次迭代教会我的

用户嘴上说「想找附近的人」，但行为数据告诉他们更在意「找到对的人」。距离是必要条件，兴趣是充分条件。产品经理不能只听用户说什么，更要看用户做什么——以及用户没说出来的是什么。

PRD Highlights

PRD 精选：需求文档不是「写出来的」，是「想清楚的」

01需求优先级体系 — 不是所有功能都值得现在做▾
优先级定义典型功能依据
P0核心必做——没它产品不成立注册登录、实名认证、发布需求、匹配申请、聊天、履约评价KANO基本型
P1优化迭代——快速验证后上拼餐扩展、运动技能标签、会员体系、个性化推荐KANO期望型
P2远期扩展——PMF后商户合作、搭子圈社区、积分体系、拼电影/拼自习KANO兴奋型
02异常流程设计 — 产品经理和「理想用户」的区别▾
定位权限被拒绝 → 不崩溃，展示手动选择城市入口 + 友好引导
发布24h无人匹配 → 自动下架 + 通知「调整时间/地点再试？」
一方放鸽子 → 违约投诉 → 系统核实 → 扣靠谱度 → 限制匹配
一方拉黑另一方 → 立即隐藏聊天入口，历史消息保留用于举证
匹配双方同时取消 → 双方均无惩罚，需求重新上架
异地登录检测 → 弹窗确认 + 10分钟未确认自动退出
03数据埋点方案 — 你不能管理你无法衡量的东西▾
埋点事件触发时机核心参数分析目的
page_view_home进入首页定位状态、分类筛选日活基数
demand_publish发布需求成功场景类型、时间、地点发布量、热门时段
match_apply申请匹配需求ID、匹配类型漏斗顶部
match_confirm匹配成功双方ID、匹配耗时核心指标：成功率
fulfill_complete履约完成匹配ID、履约时长最终转化
review_submit提交评价评分、评价长度满意度/NPS

📌 关键转化漏斗：首页浏览 → 查看详情 → 申请匹配 → 匹配成功 → 履约完成。每步流失率都是优化切入口。

04非功能需求 — 产品经理的技术边界意识▾
⚡ 性能

启动 ≤3s · 列表加载 ≤1s · 消息 ≤0.5s · 并发 ≥10000人

🔒 安全

数据加密存储 · 隐私合规 · 内容实时审核 · 异常登录检测

📱 兼容

iOS 13+ / Android 8+ · 主流机型覆盖 ≥90%

♿ 易用

核心操作 ≤3步 · 对比度 ≥4.5:1 · 无障碍适配
